# 読み上げ開始時の「プツッ」ノイズと冒頭欠落の調査レポート

- 調査日: 2026-11-02（第 4 工程で、出力ストリームの直接録音による波形測定を追加し、結論を書き直した。第 5 工程で全録音を再解析し、新しい録音で再現を確かめ、数値と推定の誤りを直した。第 6 工程では既存録音を独立に照合し、断定の範囲と再現手順を修正した。第 7 工程では落ち込みのサンプル単位の形と停止時の数値を再確認し、タップのドリフト補正を切った新しい録音で、録音側の処理によるものでないことを確かめた。末尾の各工程の節を参照）
- 対象: SimpleTTS（`/usr/bin/say` を文ごとに起動して読み上げる実装。`SimpleTTS/SayCommandSpeaker.swift`）
- 環境: macOS 27.0.1 (26A434)。既定の出力デバイスは HDMI 接続のディスプレイ **EX-LD4K432D**（48 kHz）。アプリの設定は **「システム既定の声」（= Sakura、Premium・ニューラル音声）・速度 360 語/分**。調査中は Google Chrome が出力デバイスを常時稼働させていた（約 −40 dBFS の出力を継続。後述）。
- 症状: 複数の文を連続して読み上げるとき、各文の最初の単語で「プツッ」という音割れのようなノイズが出る、または最初の単語が聞き取れない。

## 結論（要約）

**最も有力な原因候補は、既定の声を `say` でライブ再生したときに、各文の冒頭約 35〜39 ms に現れる振幅の不連続である。** CoreAudio のプロセスタップ録音と `say -o` の参照波形を照合し、既定の声の 21 回（第 7 工程の新しい録音 4 回を含む）・8 種類の文すべてで同じ形の落ち込みを確認した。アプリからの再生は、参照を用意できた 6 文が 6/6 で該当する。アプリは文ごとに `say` を起動するため、この再生開始時の現象が各文で繰り返される。

「東京の天気は晴れです。」（360 語/分）では、参照先頭を 0 とした 1856 サンプル目（48 kHz で 38.67 ms）で振幅が +0.396 から +0.020 へ落ち、約 95 サンプル（2.0 ms）の直線的なゲイン回復が続く。参照との差は最大 0.416。落ち込みの約 16 サンプル前からは、符号が 1 サンプルごとに反転する差（最大 0.020）が現れ、落ち込みの後にも続く（第 7 工程）。同じ位置の不連続は HDMI と内蔵スピーカーの録音で再現した。HDMI では、別プロセスが出力を維持している状態と、出力しているプロセスがない状態の両方で再現した。また、タップのドリフト補正の有無にかかわらず同一だった。一方、`say -o` の参照、Kyoko の 2 回、参照ファイルを `AVAudioEngine` で再生した 4 回には検出されなかった。

この比較から、調査した既定の声のライブ再生経路に依存する現象と判断する。ただし、タップは出力キューへ投入する前のバッファを直接観測していないため、合成処理・AudioQueue・HAL のどこで加工されたかは特定できない。合成チャンク境界でフェードインが掛かるという説明は仮説である。落ち込みの直前に符号交互の差が出ることから、ゲインの変化が生じた後に、ナイキスト付近まで通す線形位相の帯域制限処理を通ったと考えられる。ゲインの変化だけでは、参照が滑らかな区間で差の符号は交互にならない。ただし、その処理がどの段にあるかは分からず、発生箇所の特定にはつながらない。聴感とマイク測定も未実施であり、この波形変化が申告された「プツッ」や単語の聞き取りに与える影響は未確認である。

その他に、次の現象を区別する。

- **発話途中の無音**: 内蔵スピーカーの 1 回で 13〜23 ms の完全な無音が 3 区間あり、前工程では同時期の `AudioQueue underflow ... injecting silence` を報告している。合成の供給遅れが疑われるが、負荷との因果関係と冒頭の聞き取りへの影響は未検証。
- **操作による途中終了**: アプリは停止・移動時に `SIGTERM` を送り、録音にも文の途中終了がある。無音位置で停止した例もあり、操作のたびにクリックが出るとはいえない。
- **停止中のデバイスの起動**: 前工程では内蔵スピーカーの IO 開始時に safety violation を報告している。タップだけではスピーカー出力の欠落を判断できない。HDMI 測定時は別プロセスが出力を維持していたと報告されている。第 7 工程では、出力しているプロセスがない HDMI でも同じサンプル位置・同じ値の落ち込みが出た。このため、文ごとのデバイス停止は主因の説明として支持されない。

推奨する対策候補は、`say -o` で文の合成を完了させてから `AVAudioEngine` で再生する方式である。プローブの 4 回では冒頭の落ち込みを検出せず、3 本目を分数サンプル単位で位置合わせすると冒頭 5〜200 ms の最大差は 0.0020 だった。アプリへの組み込み、先読み、フェード付き停止、停止中のデバイスからの初回再生は未検証である。

## 現在の実装（要点）

- `SimpleTTS/SayCommandSpeaker.swift:68-108` の `speak` は呼ばれるたびに `Process` を作り、`/usr/bin/say -r <rate> [-v <voice>] -f -` を起動して本文を標準入力から渡す。
- `SimpleTTS/ReaderModel.swift:229-253` の `sentenceDidFinish` は `say` の終了通知を受けてから次の文で再び `speak` を呼ぶ。文の数だけ `say` が起動し、文と文の間に 0.9〜1.3 秒の無音（プロセス起動と音声ロード）が入る。
- `SimpleTTS/SayCommandSpeaker.swift:110-116` の `stop()` は `process.terminate()`（`SIGTERM`）。`speak` の先頭でも `stop()` を呼ぶため、再生中の「前の文」「次の文」「文脈クリック」は「再生中の `say` を即時 kill → すぐ次の `say` を起動」になる。

Auth Right: Unknown (None), promptPolicy = 0`）。これは前工程で報告された制約で、本レビューではマイク実験を再開していない。権限不足が発生した場合は、依頼どおり実験を中断して報告する。タップの用途については [Apple の公式資料](https://developer.apple.com/documentation/CoreAudio/capturing-system-audio-with-core-audio-taps) を参照。

## 測定結果

録音の波形は第 6 工程でも再解析した。音声名・デバイス状態・システムログ・合成所要時間は、特記しない限り前工程の観測記録であり、第 6 工程で新たに測定したものではない。`tmp/noise/logshow.txt` と `logstream.txt` はともに `(eval):log:1: too many arguments` だけで、本文のシステムログ引用をこの保存ファイルから再確認できなかった。`tap*.log` は録音器の稼働ログであり、`say` / coreaudiod のログではない。

### 1. ターミナルからの `say`（HDMI、既定の声、-r 360、「東京の天気は晴れです。」×3）

`say` の出力ストリーム（`tapA.wav`）と `say -o` の参照（`ref360_48k.wav`）の比較。3 回とも同一。

| 項目 | 結果 |
| --- | --- |
| 先頭 0〜10 ms のレベル差 | 小数第 1 位で 0.0 dB（この区間のレベル低下は検出せず） |
| 10 ms 〜 800 ms の各区間のレベル差 | 30〜50 ms のみ −0.3 dB、他の解析区間は小数第 1 位で 0.0 dB |
| 発話前 300 ms のピーク | −64 dBFS（開始時のポップなし） |
| 発話内の 1 ms 以上のゼロ列 | 0 |
| 末尾 | 参照の最終サンプル（1724 ms）まで届き、その後は完全な無音 |
| **38.67 ms 地点（1856 サンプル目）** | **振幅 +0.396 → +0.020 に 1 サンプルで落ち、2.0 ms で参照に戻る**（参照は +0.40 → +0.40 と連続）。失われた成分の最大 0.416（−7.6 dBFS）、最大段差 0.376（参照の同区間は 0.068） |
| 落ち込みの直前（1838〜1855 サンプル目） | 参照は −0.17 から +0.44 へ滑らかに変化し、1850〜1855 では +0.33〜+0.44 の正の値が続く。それでも差 tap − ref は +0.001, −0.003, +0.005, … −0.018, +0.020, −0.020 と 1 サンプルごとに符号が反転しながら大きくなる（第 7 工程）。5〜34 ms の差は 0.0002 以下 |
| 落ち込みの後（45〜500 ms） | 参照との差は最大 0.0063。落ち込み以外は参照と同じ波形 |

38.67 ms 地点の前後では時間ずれはなく（前後それぞれの波形相関でラグ 0 サンプル）、サンプルが失われたのではなく **振幅だけが一瞬落ちている**。0.25 ms ごとのゲインは 0.08 → 0.26 → 0.34 → 0.44 → 0.64 → 0.70 → 0.88 → 0.97 → 1.00 で、サンプルごとに当てはめると `g = 0.004 + 0.0104 × n`（n は落ちた点からのサンプル数）、つまり **0 から始まって 95 サンプル（1.99 ms）で 1 に達する直線のフェードイン**である。ただし、直前の符号交互の差（上の表）と、落ち込み後の値が ±0.02 程度で交互に振れること（+0.020, −0.015, +0.027, −0.003, …）から、タップに届いた波形は「1 サンプルでのゲイン急落」をナイキスト付近で帯域制限した形である。直線の当てはめはゲインの大まかな形を表すもので、サンプル単位で厳密に g × ref になっているわけではない。（第 4 工程の「0.05 → … → 1.0 と 2.5 ms で回復」は 1 ms 窓の包絡線比で、形を粗く見ていた。）

### 6. 第 3 工程の測定との関係

- 第 3 工程は coreaudiod のログ（IO コンテキストの開閉、client timeout、safety violation）から「文ごとの IO 開閉」を主因としたが、今回タップで波形を見ると、各文の先頭サンプルは完全に届いており、文末も参照どおり無音まで出てから止まっている。client timeout は `say` がプロセス終了時に IO コンテキストを残すために毎回記録されるが、その時点で波形は既に無音で、可聴の影響は確認できない。
- `devprobe` / `procprobe` で確認したところ、HDMI デバイスは調査中ずっと稼働中（Chrome Helper が `runningOutput=1`）で、文間でも止まっていなかった。この記録は「文ごとにデバイスが停止し、HDMI シンクのミュート解除が遅れる」という説明を支持しない。シンク自身の挙動は未測定である。別アプリが音を出していないデバイス（内蔵スピーカー単独など）では、第 3 工程の safety violation（副因 C）が残る。
- 第 3 工程の「合成波形の先頭無音が 2〜5 ms」「`[[slnc]]` が既定の声に効かない」「`-f -` と引数渡しは同一」「存在しない音声名でもエラーにならない」「`say -a ?` に HDMI が出ない」は今回も有効。

## 原因の分析

### 主因候補: `say` のライブ再生経路に依存する開始直後の不連続

- 位置は再生開始から 34.6〜38.8 ms で、文と速度で少し変わる。同じ文・同じ速度なら、出力デバイス（HDMI・内蔵スピーカー）や日時が違っても同じサンプル（例: 1856 サンプル目）で、1 サンプル単位で再現する。
- 形は「ゲインがほぼ 1 サンプルで 0 近くに落ち、約 95 サンプル（2.0 ms）で直線的に 1 に戻る」で、時間ずれはない。波形は、落ち込みの約 0.4 ms 前まで（5〜34 ms の差 0.0002 以下）と回復後（45〜500 ms）で参照と一致する。音声の途中でフェードインをもう一度やり直した形である。
- 落ち込みの直前 16 サンプルと直後に、ナイキスト付近の符号交互の差（最大約 0.02）がある。タップのドリフト補正を切った録音でも 1/1000 単位まで同一なので、補正のリサンプリングによるものではない。ゲインの変化が生じた点より後段に、線形位相の帯域制限処理があることを示唆する。ただし、その段が合成処理・AudioQueue・HAL のどこにあるかは分からない。なお、参照（`say -o`）は 11 kHz 以上の成分が −43 dB しかない（`review8/spectra.txt` の 1 行目）。`say -o` を形式指定なしで出すと 22050 Hz の CAF になる。
- `say -o`（ファイル出力）と Kyoko にはない。`AVAudioEngine` で同じデータを再生しても出ない。このため、調査した既定の声のライブ再生経路に依存すると判断する。ただし、ライブ合成とファイル合成では処理が異なり得るため、ライブ合成段階や AudioQueue・HAL の経路固有の処理を除外することはできない。出力キュー投入前の波形は未測定である。
- 出力キューの作成・開始のログは最初の音が出る前に 1 回ずつ出るだけで、落ち込みの時点に対応するログはない（第 4 工程の「キューの作り直し後の開始ランプ」という推定はログと合わないので取り下げる）。位置がデバイスや IO のタイミングに依存せず文ごとに決まることから、ストリーミング合成の 2 つ目のチャンクの先頭にフェードインが掛かっていると推定するが、内部実装は非公開で確かめられない。アプリ側から回避する手段（オプション・環境変数）は見つからなかった。
- 落ち込み位置と振幅差の文による違いは、「最初の単語で鳴る」「文によって目立ち方が違う」という症状と整合する。ただし可聴性には周囲の音声や再生環境も関係し、症状との対応は聴感確認が必要である。

### 副因 A: 合成の供給遅れによる無音挿入

前工程ではログに `minInFlight=3` と `underflow ... injecting silence` を確認したと報告している。B3 の波形にも 13〜23 ms の無音と時間ずれがある。ただし、`minInFlight` だけからバッファの総時間や遅延への耐性は決められない。CPU 負荷との関係は疑われるが、対照実験による確認はない。再生開始直後（キャッシュが冷えている、音声アセットのロード直後）ほど起きやすいと考えられるが、再現は B3 の 1 回だけで、位置との関係は確かめていない。

### 副因 B: `SIGTERM` による切断

アプリは `SIGTERM` を送るだけで、停止のフェードを制御していない。45 文目では、参照の 1429.31 ms の +0.1189 から次のサンプルで +0.0177 に急減した。その後、符号交互に減衰する小さな波形が約 1 ms 続いて終了した（`review8/tail45-samples.txt`）。第 4・5 工程の「0.119」と第 6 工程の「0.0177」の食い違いは、「最後の非ゼロサンプル（1430.31 ms）の直前 1 ms」という窓の端に 68607 サンプル目が入るかどうかの違いで、どちらも窓の取り方による値である。切断直前の振幅は 0.119 とするのが正しい。この録音はドリフト補正ありで録ったため、切断後の減衰波形が録音側の処理によるものかは区別していない。42 文目では無音部分で終了しており、操作のたびに可聴クリックが生じるという根拠はない。

### 副因 C: 停止しているデバイスでの IO 開始（条件付き）

第 3 工程のとおり、他に音を出しているアプリがないデバイスでは `say` の最初の IO サイクルが 90 ms 超かかり safety violation になる。今回の HDMI 環境では Chrome のおかげで起きなかったが、環境が変われば（内蔵スピーカー単独、Chrome を閉じる）最初の文で重なる可能性がある。

### 今回の不連続を説明する根拠がないもの・除外できる範囲

- **本文の渡し方**（`-f -` と標準入力）: 引数渡しと合成結果が完全一致（第 3 工程）。
- **文分割**（`SentenceSplitter`）: 句読点・改行・文字数で分割し、各文の前後の空白を除く。文頭の非空白文字を削る処理はない。
- **速度（`-r`）**: 落ち込みの位置をわずかに変えるだけで、180 でも出る。
- **二重起動**: アプリからの `say` は 1 文 1 プロセスで、ストリームも PID と 1 対 1。
- **ファイルに合成した波形**: `say -o` の参照には今回の不連続がない。ライブ合成と同じ内部処理であることまでは確認していない。
- **再生方式に共通するタップの異常**: `AVAudioEngine` では不連続が出ず、全方式に共通する異常という説明は支持されない。ライブ再生固有の HAL 処理の関与までは除外できない。
- **HDMI シンクだけを原因とする説明**: デバイス出力前のタップ録音に不連続があり、内蔵スピーカー宛てでも再現する。シンクで追加の欠落が起きるかは未測定。
- **冒頭サンプルの欠落**（Mac 側）: 先頭 10 ms のレベル差は小数第 1 位で 0.0 dB。タップ上で大きな欠落を示す差は見られないが、スピーカー出力の完全性を保証するものではない。

## 対策案（推奨順）

### 1. `say -o` で文ごとにファイルへ合成し、アプリ内の `AVAudioEngine` で連続再生する（プローブで波形を検証、アプリ統合は未実施）

- 合成: `say -r <rate> [-v <voice>] -o <tmp>.wav --data-format=LEF32@48000 -f -` を背景キューで実行し、次の 1〜2 文を先読みしておく（音声・速度・「システム既定の声」はそのまま使える）。`say -o` の所要時間は短い文で今の起動待ちと同程度（「東京の天気は晴れです。」で 0.76〜0.99 s）、13.6 秒の長い文で 2.1 s で、測定した文では合成時間が再生時間より短かった。次の文の合成が間に合う条件なら文間の待ち時間を短縮できるが、短文の連続や高負荷では先読みが追いつかない場合がある。
- 再生: `isPlaying` の間 `AVAudioEngine` を起動したままにし、`AVAudioPlayerNode.scheduleFile` で順に流す。出力 IO を維持すれば文間の再起動を減らせる。初回起動や出力デバイス変更時の欠落防止は別途検証する。
- 停止・移動: `AVAudioPlayerNode.stop()` の前に 10〜20 ms のゲインランプを実装し、操作時の波形と聴感を検証する。既存プローブはこの停止方法を試していない。
- 効果: ライブ再生経路を避け、合成の供給遅れを再生中の音声から切り離せる。5. の 4 回では冒頭の落ち込みを検出しなかった。ただし、再生エンジン自体のアンダーランやデバイス障害まで防ぐ保証ではない。
- 注意: 一時ファイルの掃除、`say -o` の失敗時（終了コードは 0 のまま無音ファイルになることがある。第 3 工程の観察）の扱い、文中の `-` で始まる本文は `-f -` のままで良い。`AVSpeechSynthesizer` は既定の声 Sakura を列挙できないので、本件では `say -o` の方が UI と互換。

### 2. `say` を使い続ける場合にできること（効果は限定的）

- **測定した Kyoko に変更する**: 今回の 2 回では冒頭の落ち込みを検出しなかったが、声が変わる。他の非ニューラル音声には一般化できない。副因 A・B・C は残る。
- **出力デバイスを起こしておく**（`AVAudioEngine` で無音を流す）: 副因 C だけに効く。今回の環境では副因 C は起きていないので症状は変わらない見込み。
- `[[slnc]]` の前置、`-r` の変更、`-a` の指定: 主因の位置を数 ms 動かすだけで解決しない。

### 3. 停止処理

現在の `SIGTERM` の停止では、アプリが終端波形を制御できない。1. に移行すればフェード付き停止を実装できるが、その効果は未測定である。

## この工程で確認できなかったこと

- **`say` 内部の正確な機構**（なぜ既定の声でだけ、なぜ 35〜39 ms か）。Apple の非公開実装のため、外からはログと波形で推定するまで。
- **聴感の確認**: 波形上の落ち込み（失われる成分は最大 0.416、−7.6 dBFS）がどの程度の「プツッ」に聞こえるかは耳で確認していない。聞き比べ用の `tmp/noise/verify6/listen_ab_tokyo.wav` と `listen_ab_app43.wav`（`say -o` → ライブ再生の順で冒頭 0.5 s を 3 回）を用意したので、手順 3 で聞いてほしい。
- **HDMI シンク側・スピーカー側の挙動**とマイクによる音響測定（Renga がマイクを要求しないため権限を付与できない）。
- **`AVSpeechSynthesizer.speak` の経路**で同じ不連続が出るかどうか（本件の対策には `say -o` を推奨するので優先度は低い）。

## 検証手順（次の担当者向け）

既存録音の再解析だけなら録音権限は不要である。新しい録音で権限エラーや実行環境の制約に遭遇したら、その時点で実験を中断して報告する。終了コードが 0 でも WAV が全無音なら成功扱いせず、原因を確認する。以下の `review-new` は未使用の出力先名に置き換え、既存の録音を上書きしない。

ログの確認は zsh の組み込み `log` と衝突するので `/usr/bin/log` を使う。数値解析には numpy のある Python（この機では `/usr/local/bin/python3`）を使う。

1. **ツールのビルド**
   ```sh
   cd tmp/noise
   for t in tapcap devprobe procprobe enginetest; do swiftc -O -module-cache-path /tmp/swiftmc -o $t $t.swift; done
   ```
2. **`say` のライブ再生の不連続を再現する**（背景で音を出しているプロセスがあれば `--exclude <pid>` で除く。`./procprobe 3` で分かる）
   ```sh
   mkdir review-new
   say -r 360 -o review-new/ref360_48k.wav --data-format=LEF32@48000 "東京の天気は晴れです。"
   ./tapcap review-new/tapA.wav 12 --exclude <chrome_pid> & sleep 2; say -r 360 "東京の天気は晴れです。"; wait
   /usr/local/bin/python3 -I dipscan.py review-new/tapA.wav review-new/ref360_48k.wav      # 38.6..40.1 ms に dips が 1 件（第 5 工程で直した版）
   /usr/local/bin/python3 -I cliffscan.py review-new/tapA.wav 0.3 0.25 0.12     # +39.6 ms に 0.455 -> 0.027 の崖
   /usr/local/bin/python3 -I verify6/gain.py review-new/tapA.wav review-new/ref360_48k.wav <発話の開始秒>   # 1856 サンプル目で落ち、約 95 サンプルの直線ランプ
   ```
   `cliffscan.py` の時刻はストリーム先頭から、`gain.py` の時刻は参照の先頭からなので、約 1 ms 違う（tapA では 46 サンプル）。`cliffscan.py` の「0.455 -> 0.027 in 1 sample」は、境目の前後それぞれ 3 サンプルの最大絶対値である（1853〜1855 の最大 0.4545 → 1856〜1858 の最大 0.0267）。`gain.py` の「+0.396 → +0.020」は境目をはさむ 2 サンプルの値で、どちらも同じ事象を表す。`gain.py` の開始秒は、`review8/align.py <tap> <ref>` の各ストリームの offset（秒）を使える。`cliffscan.py` をしきい値なしで使うと、参照にもある自然な急変まで崖として出るので、参照のある録音では `gain.py` を使う。zsh では `set -- $s` で単語に分かれないので、ループでは `${pair%%:*}` などで分ける。
3. **聴感**: `afplay verify6/listen_ab_tokyo.wav`（`say -o` とライブ再生の冒頭 0.5 s を交互に 3 回）を内蔵スピーカーやヘッドホンで聞き、ライブ再生の側でだけ「と」の直後にクリックが乗るか確かめる。`afplay` は `AVAudioEngine` と同じくファイル再生なので、録音した不連続をそのまま再生する。2. の `say` と `say -v Kyoko` の聞き比べも行う。
4. **アプリからの再生**: `./tapcap review-new/tapC.wav 100 --exclude <pid> &` を起動してからアプリで再生し、`cliffscan.py review-new/tapC.wav` でストリーム数・ゼロ列・終端、画面に見えている文を `say -o` で参照にして `dipscan.py review-new/tapC.wav ref1.wav ref2.wav ... --gap 0.4` で落ち込みを見る。
5. **対策案 1 の確認**: `./tapcap review-new/tapE.wav 14 --exclude <pid> & sleep 1.5; ./enginetest 0.6 ref360_48k.wav app_ref_1.wav; wait` のあと、各発話について `verify6/gain.py review-new/tapE.wav <参照> <開始秒>` で「no gain dip」、`cliffscan.py review-new/tapE.wav 0.3 0.25 0.12` で崖・ゼロ列が 0 であること。サンプル差が大きく見えるときは `verify6/subsample.py` で 1 サンプル未満のずれを測り、`verify6/fracfix.py` で補正して比べる。
